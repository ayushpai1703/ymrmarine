Root cause findings

Confirmed via live GCP access and the Cloud SQL audit log, not just the repository. Two items were reported directly this session and are already fixed in code.

Confirmed · already fixed RCA-00 — Cloud SQL ran on an expensive tier for 6 weeks

The audit log is unambiguous: the instance was created Aug 24 on db-perf-optimized-N-8, a high-end Enterprise-Plus performance tier, with 100GB SSD. It ran unchanged until Oct 7, 16:31–16:38, when you resized it yourself — briefly to db-custom-2-8192, then immediately down to the current db-custom-1-3840 (1 vCPU, 3.75GB). The October bill blends about a week on the expensive tier with the rest of the month on the now-correct one. You found and fixed this three days before this report did.

Needs your decision RCA-00b — Orphaned Compute Engine VM

instance-20260818-094020 (e2-medium) has been running since Aug 18 under GCP Console's auto-generated default name — a strong signal it was a manual, one-off creation, not part of the deploy pipeline. ~$16–17/month combined with its disk. The Load Balancer billed in the same period is confirmed legitimate (it fronts your custom domains) — only the VM is in question.

Confirmed good RCA-08 — Backups & PITR

Live-checked: automated backups on, 15 retained, binary logging enabled with 7-day transaction log retention to Cloud Storage — exactly what point-in-time recovery needs. No HA/regional failover (zonal only), a reasonable cost trade-off for a budget-constrained internal tool. One thing still worth doing: a one-time test restore to prove it actually works end to end.

High RCA-01 — Schema changes tracked nowhere

24+ loose migration files, no migration-tracking table, and 15+ pages that silently self-heal a missing column on load instead of a real schema being the source of truth. This exact pattern caused a production export failure, fixed this session — and will recur in a different shape until the pattern itself changes.

Fixed this session RCA-02 / RCA-03 — Duplicate emails & slow uploads

Both traced to the same cause: one fully separate email send — its own SMTP handshake or Gmail API token exchange — per admin recipient, repeated per upload. Collapsed into a single multi-recipient send; shipped to staging and production.

Keep Cloud SQL, or move to managed PostgreSQL?

Weighted across cost, reliability, migration safety, latency, and five other criteria. The schema has zero triggers, views, or stored procedures — the easiest possible case for a cross-engine move — but the PHP code leans on MySQL-only syntax (GROUP_CONCAT, SHOW COLUMNS, ENUM, ON UPDATE CURRENT_TIMESTAMP) in 15+ files.

Recommendation: stay on Cloud SQL for MySQL

No PostgreSQL-specific requirement exists anywhere in this codebase, and a migration wouldn't fix RCA-00 — the new engine would need rightsizing too, after paying for a 2–4 week rewrite first. A full contingency migration plan is kept on file for if that ever changes.
