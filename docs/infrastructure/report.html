Root cause findings

Ranked by severity. Two items were reported directly this session and are already fixed in code.

Critical RCA-00 — Cloud SQL cost spike

A 2504% jump this large isn't traffic growth for a ≤50-user app — it points to a tier/edition change, HA being enabled, runaway storage auto-increase, an orphaned replica, or a one-off heavy operation left running. The deploy pipeline sets no tier, edition, or storage flags, meaning the instance was sized out-of-band and this repository can't say which.

Next step: one read-only gcloud sql instances describe call, pending GCP access.

High RCA-00b — Unidentified Compute Engine / Load Balancing spend

~₹1,376/month (~$16–17) in Compute Engine, Persistent Disk, and Load Balancing charges with no matching resource in cloudbuild.yaml or the Dockerfile. Could be a legitimate load balancer fronting the custom domains, or an orphaned VM. Small in dollars, worth closing on principle.

Critical if unconfirmed RCA-08 — Backup & PITR status unknown

Nothing in the repository configures backups or point-in-time recovery — that's a console-side setting invisible to static inspection. This is the one fact that must be confirmed before any other infrastructure decision, migration included.

High RCA-01 — Schema changes tracked nowhere

24+ loose migration files, no migration-tracking table, and 15+ pages that silently self-heal a missing column on load instead of a real schema being the source of truth. This exact pattern caused a production export failure, fixed this session — and will recur in a different shape until the pattern itself changes.

Fixed this session RCA-02 / RCA-03 — Duplicate emails & slow uploads

Both traced to the same cause: one fully separate email send — its own SMTP handshake or Gmail API token exchange — per admin recipient, repeated per upload. Collapsed into a single multi-recipient send; shipped to staging and production.

Keep Cloud SQL, or move to managed PostgreSQL?

Weighted across cost, reliability, migration safety, latency, and five other criteria. The schema has zero triggers, views, or stored procedures — the easiest possible case for a cross-engine move — but the PHP code leans on MySQL-only syntax (GROUP_CONCAT, SHOW COLUMNS, ENUM, ON UPDATE CURRENT_TIMESTAMP) in 15+ files.

Recommendation: stay on Cloud SQL for MySQL

No PostgreSQL-specific requirement exists anywhere in this codebase, and a migration wouldn't fix RCA-00 — the new engine would need rightsizing too, after paying for a 2–4 week rewrite first. A full contingency migration plan is kept on file for if that ever changes.
